Lattice Lines A combinatorics & geometry explorer

Lattice Lines is a computational project that enumerates and visualises every line segment that can be drawn between any two points of an n×n integer point grid. It answers a set of combinatorics questions about those segments and provides two interactive browser-based visualisations to explore the results.

The Problem

Arrange 100 points in a 10×10 square grid where adjacent points are distance 1 apart. Draw a line between every pair of points.

  1. What is the side length of the biggest square that can be formed?
  2. How many lines are drawn in total?
  3. How many of those lines have length exactly 1?
  4. If you replace "1" with another number, can you get a bigger count for question 3?

Question 4 is the interesting one — it asks which length is most common among all the segments. Intuitively you might guess short lengths win, but the answer is a knight-move diagonal.

Known Answers

QuestionAnswerReasoning
Q1 — Biggest square side = 9 The bounding square of the 10×10 grid has corners at the four corners of the grid. Side length = cols − 1 = 9.
Q2 — Total lines 4 950 C(100, 2) = 100 × 99 / 2 = 4 950.
Q3 — Unit segments 180 90 horizontal (9 per row × 10 rows) + 90 vertical (9 per column × 10 columns).
Q4 — Winning length √5 → 288 Length √5 (squared distance 5) corresponds to the knight-move vectors (±1, ±2) and (±2, ±1). These have more placements than any other length including 1.
Why √5 wins

Length √5 has 4 distinct shapes on a 10×10 grid: vectors (−2,1), (−1,2), (1,2), (2,1). Each shape tiles the grid densely. The four shapes together produce 288 placements, beating the 180 unit segments. On a 30×30 grid √5 has 3 248 placements and remains the dominant length.

Geometry Model

Points and segments

Points are plain integer coordinates. Segments are unordered pairs of points. All distance calculations use squared distances — integer arithmetic with no floating point. A "length" is always referred to internally by its squared value (e.g. squaredLength = 5 for √5). Floating point only appears when formatting output for humans. 

data class Point(val x: Int, val y: Int)

fun Point.squaredDistanceTo(other: Point): Int {
    val dx = other.x - x
    val dy = other.y - y
    return dx*dx + dy*dy
}

data class Segment(val a: Point, val b: Point) {
    val squaredLength: Int get() = a.squaredDistanceTo(b)
}

Grid enumeration

gridPoints(rows, cols) returns all points in row-major order (y outer, x inner). allSegments(points) produces all C(n, 2) pairs using a double loop with j > i.

Critical invariant

Because points are sorted by (y, x), the vector b − a from any segment produced by allSegments always satisfies dy ≥ 0, and when dy = 0, dx > 0. This is exactly the canonical form used by shapesForSquaredLength, so the two functions are always consistent. Breaking this assumption would cause shapeIndex.getValue(key) to throw.

Shapes & Lengths

What is a shape?

Two segments have the same shape if one is a translation of the other — same direction and length, different position. A shape is identified by its canonical step vector (dx, dy).

The number of shapes for a given squared length depends on how many ways the integer can be written as a sum of two squares:

Squared lengthShapesVectors
1 (length 1)2(1,0) horizontal · (0,1) vertical
2 (length √2)2(−1,1) · (1,1) — the two diagonals
5 (length √5)4(−2,1) · (−1,2) · (1,2) · (2,1) — knight moves
25 (length 5)4(0,5) · (5,0) · (−3,4) · (3,4)
1105 (length √1105)164 decompositions × 2 signs each for dx

Unused shapes

Some shapes exist mathematically but have zero placements on a given grid — the step vector would place the endpoint outside the grid boundaries. The tile explorer greys these out so they are visible but clearly inactive.

Building & Running

The project uses the Gradle wrapper. Never invoke gradle directly. All commands below are run from the project root. 

# Compile and run all tests
./gradlew build

# Print the answers to the 4 domain questions
./gradlew run

# Run tests only
./gradlew test

# Run a single named test
./gradlew test --tests "com.fran.latticelines.LatticeAnalysisTest.unit segment count on 10x10 grid is 180"

# Generate the tile explorer (lattice.html)
./gradlew generateViz

# Generate the curve explorer (curve.html)
./gradlew generateCurve

# Remove compiled classes and build outputs
./gradlew clean

Both generateViz and generateCurve write their HTML files to the project root (not the app/ subdirectory). Open either file directly in a browser — no web server required.

Browser requirement for lattice.html

lattice.html uses the DecompressionStream API to decompress its embedded data at load time. This requires Chrome 80+, Firefox 113+, or Safari 16.4+. curve.html has no such requirement.

Tile Explorer — lattice.html

An interactive page that lets you browse every segment in the grid, organised by length and shape. Covers all grid sizes from 2×2 to 30×30; opens on 10×10 by default.

Toolbar

  • Grid dropdown — switch between any grid size 2×2 → 30×30. Automatically selects the length with the most segments for the new grid.
  • Length dropdown — every distinct segment length in the current grid, ordered by ascending squared distance, with segment count and shape count shown.
  • Mode toggle — switch between All segments and Shapes mode.
  • Random — jump to a random segment tile (disabled in Shapes mode).

All segments mode

One tile per placement of the selected length on the grid. Each tile shows the grid (as a bounding box for dense grids, or full grid lines for sparse ones) with the segment drawn over it. Tiles are colour-coded by shape — all placements of the same shape share a colour.

Shapes mode

One tile per canonical shape for the selected length. The segment is drawn at a consistent scale anchored at a corner, so all shapes fan out visually for easy comparison. Shapes with zero placements on the current grid are greyed out, and the header reports how many are unused.

Detail panel

Clicking any tile opens the full-detail view: a larger SVG showing the segment in context (all grid dots visible), plus the exact coordinates, step vector, and length. Prev / Next buttons step through all tiles in order.

Stats bar

At the bottom of the tile panel: two side-by-side tables showing the top 5 and bottom 5 lengths by segment count for the current grid. The currently selected length is highlighted in blue. Updates on every grid or length change.

Curve Explorer — curve.html

A line chart showing the segment count for every distinct length, for a chosen grid size. Switch grid sizes with a dropdown; both axes rescale so the dominant length always peaks near the top of the chart.

  • X axis: actual segment length (√squaredLength as a floating-point number)
  • Y axis: number of segments at that length
  • Hover: snaps to the nearest data point and shows a tooltip with the exact length notation (e.g. √5 ≈ 2.236) and count

This file embeds only counts (no segment coordinates), so it is small (~52 KB) and has no decompression requirement.

Data Encoding

lattice.html embeds all segment data for 29 grid sizes. Storing this naïvely as JSON would produce a ~31 MB file. Two optimisations bring it to ~5.6 MB before compression.

Optimisation 1 — anchor-only storage

Every segment belongs to a shape with a known step vector (dx, dy). Instead of storing both endpoints [x1, y1, x2, y2], only the anchor point [x1, y1] is stored. The endpoint is reconstructed as (x1 + dx, y1 + dy) in JS at load time. This halves the coordinate data.

Optimisation 2 — base-36 flat strings

Coordinates are integers 0–29 (for the largest 30×30 grid). Base-36 maps 0–9 to '0'–'9' and 10–35 to 'a'–'z', so every value 0–29 fits in a single character ('0'–'t'). Each segment's anchor becomes exactly 2 characters with no brackets, commas, or spaces. All placements for one shape are concatenated into a single flat string.

Before and after

FormatExample (sq=1, shape (1,0), 3×3 grid)
Naïve JSON [[0,0,1,0],[1,0,2,0],[0,1,1,1],[1,1,2,1],[0,2,1,2],[1,2,2,2]]

The JS decoder iterates the string two characters at a time: 

for (var j = 0; j < str.length; j += 2) {
    var ax = b36[str[j]],  ay = b36[str[j+1]];
    result[j/2] = [ax, ay, ax + dx, ay + dy];
}

Compression

After encoding, the Kotlin build step compresses the JSON with GZip and base64-encodes the binary result so it can be embedded as a string literal in HTML. The browser decompresses it at page load using the DecompressionStream API.

Design principle

Both visualisations are fully self-contained single HTML files with no external dependencies, no CDN requests, and no build step on the frontend side. They work by opening the file directly in a browser.
